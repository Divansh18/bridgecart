# Production k3s guidance

`values-prod.yaml` is a **review template**, not production-ready settings. It renders the same WordPress, MariaDB, bootstrap, ingress, PVC, and NetworkPolicy templates used locally. Before a production install, replace `shop.example.com`, the public HTTPS URL, the Secret names, admin email, and all three storage classes. The ingress class must match the actual Traefik installation. A TLS Secret must already exist in the release namespace. Do not put secret values in values files or `--set` arguments.

Create a production Secret through your secret manager/operator with these keys: `mariadb-root-password`, `mariadb-password`, `wordpress-admin-password`, `wordpress-auth-key`, `wordpress-secure-auth-key`, `wordpress-logged-in-key`, `wordpress-nonce-key`, `wordpress-auth-salt`, `wordpress-secure-auth-salt`, `wordpress-logged-in-salt`, and `wordpress-nonce-salt`. Keep these stable across pod restarts. Production secret creation and rotation are deliberately separate from the local `make store-secrets` script.

Set the WordPress and MariaDB PVC storage classes to a durable class supported by the target cluster and size them for growth. The chart runs one WordPress pod and one MariaDB pod with ReadWriteOnce claims. This is **not highly available**; a node failure can interrupt or strand the store depending on the storage class. The chart does not configure database replication, external MariaDB, snapshots, or backup jobs. Establish tested MariaDB dumps/physical backups and WordPress content backups before live orders. Persistence alone is not a backup.

The chart's MariaDB Service is internal. WordPress and the team API have separate Ingresses; MariaDB and PostgreSQL do not. NetworkPolicy enforcement depends on the production k3s CNI/controller and Traefik labels; validate the paths and denied-connection test after installation. DNS egress to CoreDNS and bootstrap HTTPS egress to WordPress.org must work. If the production cluster is air-gapped, prepare an approved plugin artifact and adapt the bootstrap explicitly; do not silently install a different version.

Production values set `bootstrap.makeStoreLive: false` and `bootstrap.makeShopHomepage: false`. A fresh WooCommerce store can remain in Coming soon mode while it is prepared, and its homepage stays under administrator control. Review checkout, shipping, legal pages, and TLS before switching Site visibility to Live in WooCommerce admin. The local demo's first-bootstrap changes are not applied in production.

The bootstrap pins WooCommerce to 11.2.1. To upgrade, back up database and content, review the target plugin's compatibility, change `woocommerceVersion`, set `allowPluginUpgrade: true` for that reviewed Helm upgrade, and observe the Job and storefront. Restore `allowPluginUpgrade: false` afterward. The Job rejects downgrades. `helm rollback` can restore Kubernetes manifests and prior image references but **cannot automatically reverse** WordPress/WooCommerce database migrations, changed orders, or content. Restore a coordinated backup if application data must roll back. MariaDB major-version upgrades need their own documented migration plan; this chart does not automate them.

`helm uninstall bridgecart -n <namespace>` removes workloads and services but leaves the store PVCs and, when enabled, the PostgreSQL PVC (`helm.sh/resource-policy: keep`). A completed hook Job may also remain. Inspect retained PVCs before any intentional deletion. Deleting a PVC under the local-path class deletes its backing volume; deleting a k3d cluster can remove local data. Never use cluster deletion as routine application cleanup.

## WooCommerce MCP production values

`woocommerceMcp.enabled` renders the same internal Deployment, ClusterIP Service, and NetworkPolicies as local. The production values file enables it as a review template; replace `registry.example.com/bridgecart/woocommerce-mcp:0.3.4` with a built, trusted, immutable image reference. Provide pre-created Kubernetes Secrets named by `woocommerceMcp.apiSecret` (keys `consumer-key`, `consumer-secret`) and `woocommerceMcp.bearerSecret` (key `token`). Do not run the local provisioner against production. Create a dedicated WooCommerce `shop_manager` user and `read_write` REST API key through a controlled production process or secret manager, then arrange for the same key pair in the API Secret. The bearer token is independent and should be distributed only to the future gateway. Never place credentials in values, shell arguments, release notes, or CI logs.

The MCP Deployment uses non-root UID/GID 10001 and a read-only root filesystem, matching its own image. Its readiness depends on the store REST API; liveness does not. Only future gateway-labeled pods may reach TCP 8001 in production; there is no MCP Ingress or NodePort. The production CNI must enforce these policies. If WordPress public HTTPS terminates at Traefik while pod-to-pod traffic remains HTTP, WooCommerce OAuth signs with the public host and the internal HTTP scheme. WordPress's Apache rewrite rules must preserve the `Authorization` header; verify this on the deployed image. Publish the MCP image and Secrets before enabling the production values. Keep existing backup and rollback cautions: Helm image rollback does not undo product or order writes.

## Team API and PostgreSQL production values

The same backend/PostgreSQL templates render in both environments. Replace `backend.host`, trusted image reference, ingress class/TLS Secret, `backend.corsOrigins`, PostgreSQL storage class/size, and Secret names in `values-prod.yaml`. Keep `backend.cookieSecure: true`; `SameSite=None` also requires Secure. Provision `postgres.credentialsSecret` with `password` and a matching `database-url` (`postgresql+asyncpg://...`), and `backend.initialAdminSecret` with `admin-email` and a strong generated `admin-password`, using a production secret manager. Do not pass these values through Helm flags or commit them. The initial-admin bootstrap creates the account only when no users exist; later deployments never reset its password. Production administrator recovery/rotation needs an explicit controlled procedure, not a chart upgrade.

On a fresh release, deploy the store and PostgreSQL first with `backend.enabled=false` and `postgres.enabled=true`, and wait for PostgreSQL readiness. Then deploy with the final production values and the trusted backend image. The pre-upgrade migration Job runs Alembic and initial-admin bootstrap before backend readiness; failed Jobs remain for inspection. Backend readiness also requires the expected Alembic revision. Plan schema changes as forward migrations and take a tested PostgreSQL backup before upgrades. `helm rollback` does not reverse a database migration, session/key write, or password change.

PostgreSQL is a single replica with a retained RWO claim and no database replication or backup Job. Choose durable storage, backup and restore procedures, and a production CNI that enforces the rendered policies. Only backend and migration pods may connect to PostgreSQL on TCP 5432; Traefik reaches backend TCP 8000; backend and migration pods use CoreDNS. PostgreSQL has no Ingress, NodePort, or permitted egress. The backend image is non-root with a read-only filesystem; the official PostgreSQL entrypoint prepares its own data directory without a forced UID. Production login rate limiting remains per process, so use one backend replica until a shared limiter is added and tested. Gateway API-key use and audit controls remain milestone 4B.
