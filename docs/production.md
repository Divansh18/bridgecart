# Production k3s guidance

`values-prod.yaml` is a **review template**, not production-ready settings. It renders the same WordPress, MariaDB, bootstrap, ingress, PVC, and NetworkPolicy templates used locally. Before a production install, replace `shop.example.com`, the public HTTPS URL, the Secret names, admin email, and both storage classes. The ingress class must match the actual Traefik installation. A TLS Secret must already exist in the release namespace. Do not put secret values in values files or `--set` arguments.

Create a production Secret through your secret manager/operator with these keys: `mariadb-root-password`, `mariadb-password`, `wordpress-admin-password`, `wordpress-auth-key`, `wordpress-secure-auth-key`, `wordpress-logged-in-key`, `wordpress-nonce-key`, `wordpress-auth-salt`, `wordpress-secure-auth-salt`, `wordpress-logged-in-salt`, and `wordpress-nonce-salt`. Keep these stable across pod restarts. Production secret creation and rotation are deliberately separate from the local `make store-secrets` script.

Set both PVC storage classes to a durable class supported by the target cluster and size them for growth. The chart runs one WordPress pod and one MariaDB pod with ReadWriteOnce claims. This is **not highly available**; a node failure can interrupt or strand the store depending on the storage class. The chart does not configure database replication, external MariaDB, snapshots, or backup jobs. Establish tested MariaDB dumps/physical backups and WordPress content backups before live orders. Persistence alone is not a backup.

The chart's MariaDB Service is internal. Only WordPress has Ingress. NetworkPolicy enforcement depends on the production k3s CNI/controller and Traefik labels; validate the paths and denied-connection test after installation. DNS egress to CoreDNS and bootstrap HTTPS egress to WordPress.org must work. If the production cluster is air-gapped, prepare an approved plugin artifact and adapt the bootstrap explicitly; do not silently install a different version.

Production values set `bootstrap.makeStoreLive: false`. A fresh WooCommerce store can remain in Coming soon mode while it is prepared. Review checkout, shipping, legal pages, and TLS before switching Site visibility to Live in WooCommerce admin. The local demo's first-bootstrap visibility change is not applied in production.

The bootstrap pins WooCommerce to 11.2.1. To upgrade, back up database and content, review the target plugin's compatibility, change `woocommerceVersion`, set `allowPluginUpgrade: true` for that reviewed Helm upgrade, and observe the Job and storefront. Restore `allowPluginUpgrade: false` afterward. The Job rejects downgrades. `helm rollback` can restore Kubernetes manifests and prior image references but **cannot automatically reverse** WordPress/WooCommerce database migrations, changed orders, or content. Restore a coordinated backup if application data must roll back. MariaDB major-version upgrades need their own documented migration plan; this chart does not automate them.

`helm uninstall bridgecart -n <namespace>` removes workloads and services but leaves both chart PVCs (`helm.sh/resource-policy: keep`). A completed hook Job may also remain. Inspect retained PVCs before any intentional deletion. Deleting a PVC under the local-path class deletes its backing volume; deleting a k3d cluster can remove local data. Never use cluster deletion as routine application cleanup.
