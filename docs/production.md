# Production k3s guidance

`values-prod.yaml` is a **review template**, not production-ready settings. It renders the same WordPress, MariaDB, bootstrap, ingress, PVC, and NetworkPolicy templates used locally. Before a production install, replace `shop.example.com`, the public HTTPS URL, the Secret names, admin email, and all three storage classes. The ingress class must match the actual Traefik installation. A TLS Secret must already exist in the release namespace. Do not put secret values in values files or `--set` arguments.

Create a production Secret through your secret manager/operator with these keys: `mariadb-root-password`, `mariadb-password`, `wordpress-admin-password`, `wordpress-auth-key`, `wordpress-secure-auth-key`, `wordpress-logged-in-key`, `wordpress-nonce-key`, `wordpress-auth-salt`, `wordpress-secure-auth-salt`, `wordpress-logged-in-salt`, and `wordpress-nonce-salt`. Keep these stable across pod restarts. Production secret creation and rotation are deliberately separate from the local `make store-secrets` script.

Set the WordPress and MariaDB PVC storage classes to a durable class supported by the target cluster and size them for growth. The chart runs one WordPress pod and one MariaDB pod with ReadWriteOnce claims. This is **not highly available**; a node failure can interrupt or strand the store depending on the storage class. The chart does not configure database replication, external MariaDB, snapshots, or backup jobs. Establish tested MariaDB dumps/physical backups and WordPress content backups before live orders. Persistence alone is not a backup.

The chart's MariaDB Service is internal. WordPress and the team API have separate Ingresses; MariaDB and PostgreSQL do not. NetworkPolicy enforcement depends on the production k3s CNI/controller and Traefik labels; validate the paths and denied-connection test after installation. DNS egress to CoreDNS and bootstrap HTTPS egress to WordPress.org must work. If the production cluster is air-gapped, prepare an approved plugin artifact and adapt the bootstrap explicitly; do not silently install a different version.

Production values set `bootstrap.makeStoreLive: false` and `bootstrap.makeShopHomepage: false`. A fresh WooCommerce store can remain in Coming soon mode while it is prepared, and its homepage stays under administrator control. Review checkout, shipping, legal pages, and TLS before switching Site visibility to Live in WooCommerce admin. The local demo's first-bootstrap changes are not applied in production.

The bootstrap pins WooCommerce to 11.2.1. To upgrade, back up database and content, review the target plugin's compatibility, change `woocommerceVersion`, set `allowPluginUpgrade: true` for that reviewed Helm upgrade, and observe the Job and storefront. Restore `allowPluginUpgrade: false` afterward. The Job rejects downgrades. `helm rollback` can restore Kubernetes manifests and prior image references but **cannot automatically reverse** WordPress/WooCommerce database migrations, changed orders, or content. Restore a coordinated backup if application data must roll back. MariaDB major-version upgrades need their own documented migration plan; this chart does not automate them.

`helm uninstall bridgecart -n <namespace>` removes workloads and services but leaves the store PVCs and, when enabled, the PostgreSQL PVC (`helm.sh/resource-policy: keep`). A completed hook Job may also remain. Inspect retained PVCs before any intentional deletion. Deleting a PVC under the local-path class deletes its backing volume; deleting a k3d cluster can remove local data. Never use cluster deletion as routine application cleanup.

## WooCommerce MCP production values

`woocommerceMcp.enabled` renders the same internal Deployment, ClusterIP Service, and NetworkPolicies as local. The production values file enables it as a review template; replace `registry.example.com/bridgecart/woocommerce-mcp:0.3.4` with a built, trusted, immutable image reference. Provide pre-created Kubernetes Secrets named by `woocommerceMcp.apiSecret` (keys `consumer-key`, `consumer-secret`) and `woocommerceMcp.bearerSecret` (key `token`). Do not run the local provisioner against production. Create a dedicated WooCommerce `shop_manager` user and `read_write` REST API key through a controlled production process or secret manager, then arrange for the same key pair in the API Secret. The bearer token is independent and should be distributed only to the backend gateway. Never place credentials in values, shell arguments, release notes, or CI logs.

The MCP Deployment uses non-root UID/GID 10001 and a read-only root filesystem, matching its own image. Its readiness depends on the store REST API; liveness does not. Only backend gateway pods may reach TCP 8001 in production; there is no MCP Ingress or NodePort. The production CNI must enforce these policies. If WordPress public HTTPS terminates at Traefik while pod-to-pod traffic remains HTTP, WooCommerce OAuth signs with the public host and the internal HTTP scheme. WordPress's Apache rewrite rules must preserve the `Authorization` header; verify this on the deployed image. Publish the MCP image and Secrets before enabling the production values. Keep existing backup and rollback cautions: Helm image rollback does not undo product or order writes.

## Team API and PostgreSQL production values

The same backend/PostgreSQL templates render in both environments. Replace `backend.host`, trusted image reference, ingress class/TLS Secret, `backend.corsOrigins`, PostgreSQL storage class/size, and Secret names in `values-prod.yaml`. Keep `backend.cookieSecure: true`; `SameSite=None` also requires Secure. Provision `postgres.credentialsSecret` with `password` and a matching `database-url` (`postgresql+asyncpg://...`), and `backend.initialAdminSecret` with `admin-email` and a strong generated `admin-password`, using a production secret manager. Do not pass these values through Helm flags or commit them. The initial-admin bootstrap creates the account only when no users exist; later deployments never reset its password. Production administrator recovery/rotation needs an explicit controlled procedure, not a chart upgrade.

On a fresh release, deploy the store and PostgreSQL first with `backend.enabled=false` and `postgres.enabled=true`, and wait for PostgreSQL readiness. Then deploy with the final production values and the trusted backend image. The pre-upgrade migration Job runs Alembic and initial-admin bootstrap before backend readiness; failed Jobs remain for inspection. Backend readiness also requires the expected Alembic revision. Plan schema changes as forward migrations and take a tested PostgreSQL backup before upgrades. `helm rollback` does not reverse a database migration, session/key write, or password change.

PostgreSQL is a single replica with a retained RWO claim and no database replication or backup Job. Choose durable storage, backup and restore procedures, and a production CNI that enforces the rendered policies. Only backend and migration pods may connect to PostgreSQL on TCP 5432; Traefik reaches backend TCP 8000; backend and migration pods use CoreDNS. PostgreSQL has no Ingress, NodePort, or permitted egress. The backend image is non-root with a read-only filesystem; the official PostgreSQL entrypoint prepares its own data directory without a forced UID. Production login rate limiting remains per process, so use one backend replica until a shared limiter is added and tested. Gateway API-key use and audit controls are included in milestone 4B.

## Gateway production values

The same gateway and demo-service templates render under `values-local.yaml` and `values-prod.yaml`. Publish reviewed immutable references for `backend.image`, `inventoryMcp.image`, and `shippingMcp.image`. The production example names are placeholders. Pre-create the Secret named by `backend.gateway.encryptionSecret` with key `fernet-key` containing a valid Fernet key, plus separate `token` Secrets named by `inventoryMcp.bearerSecret` and `shippingMcp.bearerSecret`. Keep the existing WooCommerce bearer and REST credentials separate. Provision these through a production secret manager or controlled private files; the local generator is not a production rotation mechanism. Back up the Fernet key along with PostgreSQL, since encrypted registrations cannot be read without it. The migration Job receives seed bearers only to create missing registrations; the long-running backend receives the encryption key, not seed bearers.

Set `backend.gateway.allowedUrls` to the exact internal MCP URLs for the release and review them with the rendered egress NetworkPolicy. The first three entries seed WooCommerce, inventory, and shipping respectively; additional entries may be registered by an admin only after matching `backend.gateway.extraEgress` component/port entries and upstream ingress policy are added in values. No upstream Service gets Ingress, NodePort, or LoadBalancer. By default, backend egress allows only PostgreSQL TCP 5432, CoreDNS TCP/UDP 53, and the three named MCP pod selectors on 8001–8003; reviewed `extraEgress` entries add only their labeled component and port. WooCommerce MCP alone may reach WordPress TCP 80 and CoreDNS; inventory and shipping have no allowed egress. The production CNI must enforce ingress **and** egress policy; test both directions before trusting it. Exact URL allowlisting, denial of URL userinfo/IP literals/localhost, gateway rejection of all upstream redirects, `trust_env=False`, and pod-selector egress provide defense against credential exfiltration and DNS rebinding. Cluster operators and node-origin traffic remain outside ordinary pod policy.

The public MCP URL is `https://<backend.host>/mcp` behind the backend TLS Ingress. Browser session cookies and user API keys are different credentials. Keep backend at one replica until registry cache invalidation and login limits have a shared coordinator. The 15-second per-process discovery cache can display stale catalog metadata; execution still reads enabled state from PostgreSQL. Take a PostgreSQL backup and keep the matching Fernet key before upgrades. Alembic upgrades are forward migrations; `helm rollback` restores manifests but does not reverse registry edits, audits, key changes, store writes, or database migrations. A crash may leave a `started` audit row and a timed-out write may have succeeded upstream; reconcile before retrying a write.

## Dashboard production values

Set `frontend.host`, `frontend.gatewayUrl`, `frontend.image`, `frontend.ingress.className`, and `frontend.ingress.tls.secretName` for the public HTTPS dashboard. Provide DNS and TLS for the dashboard and API hosts. Keep `backend.cookieSecure: true` and ensure both `/api` and the SPA are served on the dashboard origin. The chart's `/api/` Ingress uses the Traefik Middleware CRD to strip the prefix before sending requests to FastAPI; verify that CRD and its namespace-scoped reference on the target k3s cluster. The API host remains available for external MCP clients at `/mcp`. Do not point browsers to cluster-internal Service names.

The frontend is a single unprivileged Nginx pod with no PVC; build or publish its pinned image before enabling it. Its runtime `/config.js` contains only the public gateway URL, never credentials. Frontend NetworkPolicy allows ingress from the configured Traefik pod selector and denies egress. A single replica and the existing in-memory login limiter are not high-availability designs. Back up PostgreSQL, MariaDB, and WordPress data before upgrades; a frontend rollback cannot reverse backend schema or store data changes.

## Anthropic chat deployment

`backend.anthropic.enabled` defaults to false in base/production values and is true locally. The local `make anthropic-secret` helper is fixed to `k3d-bridgecart/bridgecart` and must not be used for production. Have a production secret manager create a dedicated Secret with key `ANTHROPIC_API_KEY`, set its name in `backend.anthropic.secretName`, select a supported pinned Claude model identifier in `backend.anthropic.model`, then enable the value. The backend Deployment uses an optional `secretKeyRef`; absence of the Secret leaves chat at 503 and does not break other features. The migration Job and browser never receive this key. Restart backend pods after Secret rotation. Keep the value out of Helm values, command arguments, CI output, and application logs.

The backend needs public TCP 443 egress for Anthropic. The chart's standard NetworkPolicy permits **all public IPv4 HTTPS destinations** while excluding private, loopback, carrier-grade NAT, link-local, and multicast ranges; ordinary NetworkPolicy cannot pin egress to `api.anthropic.com` by DNS name. Review this broad public HTTPS allowance, DNS resolution, node/NAT paths, and any production egress proxy or FQDN-aware policy before enabling chat. Traefik's `ServersTransport` sets a 60-second backend response-header timeout above the 45-second chat deadline; ensure the production entrypoint and any outer load balancer also permit that duration. Provider availability is not an application liveness condition.
