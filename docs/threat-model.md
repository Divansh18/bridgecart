# Threat model

The current local store has a public HTTP ingress on loopback port 8088 for development. It has no TLS, and its demo checkout uses cash on delivery. Do not use it for real customers or payment information. WordPress admin and database credentials reside in a pre-created Kubernetes Secret. The local secret generator uses temporary 0600 files and never prints values; the Secret is not committed. Kubernetes operators with Secret read permission can still retrieve them.

NetworkPolicies reduce pod-to-pod reachability: only the labeled WordPress and bootstrap pods may connect to MariaDB, and Traefik and WooCommerce MCP may reach WordPress through its pod network. The bootstrap pod has public HTTPS egress for a version-pinned plugin download. Host access, node-originated traffic, and privileged Kubernetes actors remain outside these pod policies. Verify enforcement on each target k3s cluster rather than treating YAML presence as proof.

Local-path PVCs preserve data across pod replacement on the same node but provide no cross-node redundancy or backup. Production requires TLS, durable storage, backup and restore exercises, secret management, and a review of WordPress/WooCommerce updates. Team authorization is implemented for the API; gateway routing and per-tool auditing remain milestone 4B work.

## Milestone-three MCP boundary

The WooCommerce API key and MCP bearer token are separate Kubernetes Secrets. The dedicated shop-manager key can read/write store resources and is held only by the MCP service. The bearer protects every Streamable HTTP transport request but does not identify a team member or authorize individual tool calls. The future gateway must authenticate users, authorize tool use, and audit each call before reaching MCP. Tools expose reduced order fields to avoid unnecessary customer contact data. NetworkPolicies block direct MCP-to-MariaDB traffic and public MCP access, but correctness depends on a policy-enforcing CNI and Secret RBAC. OAuth on internal HTTP is placed in `Authorization`, avoiding query-string credential logging; future production deployments should prefer TLS for sensitive east-west traffic where supported.

## Team API (milestone 4A)

The local API Ingress is HTTP on loopback port 8088; use only demo identities and no real personal or payment data. Production must use TLS and Secure cookies. Passwords are salted scrypt hashes. Opaque session, CSRF, invitation, and gateway API-key tokens are CSPRNG-generated and stored only as purpose-separated SHA-256 hashes. Raw invitation tokens and API keys are returned only at creation; response handling by clients must protect them. The request-validation handler omits submitted values from 422 errors. Backend access logging is disabled in the deployed image. Kubernetes Secret readers can access the backend database and initial-admin Secrets. A compromised backend process can access its injected database URL; the bootstrap password is injected only into the migration Job.

HttpOnly session cookies are distinct from gateway Bearer API keys. Cookie-authenticated mutations require a matching readable CSRF cookie and `X-CSRF-Token` header tied to the server-side session. SameSite=Lax is set locally; production values require Secure. The API checks user activity and token revocation on every request. Admins can invite and deactivate members or manage their keys; member routes enforce ownership in SQL queries. Initial admin provisioning is Secret-backed and idempotent, with no public signup or default password. The local invitation helper writes a 0600 token file for private handoff. There is no email delivery, password reset, MFA, shared rate-limit store, or audit log yet. The in-memory login limiter protects only one replica and resets on restart.

PostgreSQL has no public Service or Ingress. Its NetworkPolicy admits only backend and migration pods; backend ingress admits Traefik, and its egress permits PostgreSQL and DNS. A compromised Kubernetes operator, node-originated traffic, or an unenforced CNI remains outside these pod controls. PostgreSQL's local-path PVC persists across backend pod replacement but is not a backup. The future gateway must authorize each MCP action using the authenticated user and record audit events; a valid API key alone does not currently enable MCP routing.
