# Threat model

The current local store has a public HTTP ingress on loopback port 8088 for development. It has no TLS, and its demo checkout uses cash on delivery. Do not use it for real customers or payment information. WordPress admin and database credentials reside in a pre-created Kubernetes Secret. The local secret generator uses temporary 0600 files and never prints values; the Secret is not committed. Kubernetes operators with Secret read permission can still retrieve them.

NetworkPolicies reduce pod-to-pod reachability: only the labeled WordPress and bootstrap pods may connect to MariaDB, and Traefik and WooCommerce MCP may reach WordPress through its pod network. The bootstrap pod has public HTTPS egress for a version-pinned plugin download. Host access, node-originated traffic, and privileged Kubernetes actors remain outside these pod policies. Verify enforcement on each target k3s cluster rather than treating YAML presence as proof.

Local-path PVCs preserve data across pod replacement on the same node but provide no cross-node redundancy or backup. Production requires TLS, durable storage, backup and restore exercises, secret management, and a review of WordPress/WooCommerce updates. Team authorization, gateway routing, per-tool auditing, and bounded dashboard chat are implemented.

## Milestone-three MCP boundary

The WooCommerce API key and MCP bearer token are separate Kubernetes Secrets. The dedicated shop-manager key can read/write store resources and is held only by the MCP service. The upstream bearer protects its Streamable HTTP transport but does not identify a team member; the gateway maps a separate user API key to each audited call. The gateway authenticates a user API key on every transport request and tool execution, and records each authenticated attempt before dispatch. Tools expose reduced order fields to avoid unnecessary customer contact data. NetworkPolicies block direct MCP-to-MariaDB traffic and public MCP access, but correctness depends on a policy-enforcing CNI and Secret RBAC. OAuth on internal HTTP is placed in `Authorization`, avoiding query-string credential logging; future production deployments should prefer TLS for sensitive east-west traffic where supported.

## Team API (milestone 4A)

The local API Ingress is HTTP on loopback port 8088; use only demo identities and no real personal or payment data. Production must use TLS and Secure cookies. Passwords are salted scrypt hashes. Opaque session, CSRF, invitation, and gateway API-key tokens are CSPRNG-generated and stored only as purpose-separated SHA-256 hashes. Raw invitation tokens and API keys are returned only at creation; response handling by clients must protect them. The request-validation handler omits submitted values from 422 errors. Backend access logging is disabled in the deployed image. Kubernetes Secret readers can access the backend database and initial-admin Secrets. A compromised backend process can access its injected database URL; the bootstrap password is injected only into the migration Job.

The Anthropic API key has its own Kubernetes Secret. The local helper accepts it only through a hidden terminal prompt and passes it to `kubectl` on stdin; it prints neither the key nor Secret contents. Helm injects it only into the backend Deployment when enabled, so the backend pod and Kubernetes Secret readers become trusted holders. The key is never put in model messages and is not available to the frontend or migration Job. Kubernetes Secret storage and API audit policy must be reviewed separately for production; a Secret is not by itself an encryption or access-control guarantee.

HttpOnly session cookies are distinct from gateway Bearer API keys. Cookie-authenticated mutations require a matching readable CSRF cookie and `X-CSRF-Token` header tied to the server-side session. SameSite=Lax is set locally; production values require Secure. The API checks user activity and token revocation on every request. Admins can invite and deactivate members or manage their keys; member routes enforce ownership in SQL queries. Initial admin provisioning is Secret-backed and idempotent, with no public signup or default password. The local invitation helper writes a 0600 token file for private handoff. There is no email delivery, password reset, MFA, or shared rate-limit store. Tool attempts are audited; login and registry mutations are not yet a general security-event audit. The in-memory login limiter protects only one replica and resets on restart.

PostgreSQL has no public Service or Ingress. Its NetworkPolicy admits only backend and migration pods; backend ingress admits Traefik, and its egress permits PostgreSQL, CoreDNS, the three approved MCP pod selectors, and public IPv4 HTTPS when enabled for chat or public MCP registration. A compromised Kubernetes operator, node-originated traffic, or an unenforced CNI remains outside these pod controls. PostgreSQL's local-path PVC persists across backend pod replacement but is not a backup. The gateway now uses active user API keys for MCP routing and stores audit records with user/key/server snapshots.

### Member-to-member impact

A member cannot manage upstream registrations or other members, read another member's API-key metadata, or view another member's audit rows; the backend enforces these boundaries, not just the dashboard. Revoking a member's key or deactivating the account blocks its next authenticated gateway request. All active members currently share the same enabled gateway tool catalog, including WooCommerce write tools. A member can therefore create products or change order status in the shared store and affect what other members see, even without seeing upstream credentials. Per-user or per-tool permissions are an unimplemented optional enhancement, so invite only trusted teammates and use audits to attribute changes. A compromised member key has that member's gateway tool authority until revocation; it cannot grant admin registry access through the session API.

## Gateway and upstream trust

Cluster-internal MCP destinations require exact URLs in `backend.gateway.allowedUrls`, with no URL userinfo, IP literals, loopback host, or unapproved path/port. Admins can also register public HTTPS endpoints on TCP 443 when `backend.gateway.allowPublicHttps=true`; local/internal DNS suffixes, credentials in URLs, queries, fragments, redirects, and unsafe custom headers are rejected. Proxy environment variables are ignored. The gateway transport rejects redirects before SDK replay, including writes. Backend NetworkPolicy egress allows only approved internal MCP pod selectors/ports plus public IPv4 TCP 443, excluding private, loopback, link-local, and metadata ranges. Ordinary NetworkPolicy cannot restrict HTTPS egress by DNS name. A public DNS name resolving into cluster or private space should be blocked by a correctly enforcing CNI, but production operators must verify Service translation, DNS, and policy behavior and use an egress proxy or FQDN-aware CNI for tighter control. A compromised cluster DNS, host process, node, or policy controller remains a residual risk; internal bearer traffic is HTTP until an east-west TLS design is added.

Stored upstream bearer/custom-header values are Fernet-encrypted in PostgreSQL and decrypted only in the gateway process. The Fernet key is a separate Kubernetes Secret. Database-only compromise does not reveal those values without the key; a compromised backend process or Secret reader can access both. Key loss prevents credential recovery; key rotation needs coordinated re-encryption. Admin read APIs return only `has_credential`. Custom headers are limited to safe `X-` names and reject Host, proxy/forwarding, hop-by-hop, and method-override headers. The gateway sends its stored upstream credential, never the user's bearer. The WooCommerce REST key remains only in its own MCP Service.

Gateway user API keys are hashed in PostgreSQL and checked on every HTTP transport request and at the shared tool-execution boundary. Stateless MCP sessions do not authenticate callers. The gateway rechecks server enabled/removal state even with cached metadata. Tool descriptions, schemas, and results are untrusted; limits bound tool counts, schema/argument sizes, on-wire response bytes, and returned result sizes, but clients must still guard against prompt injection and unsafe rendering. Upstream tool errors are replaced with safe categories, and arguments/results are not stored in audits. A started audit row must commit before dispatch; if it cannot, the call fails closed. A process crash can leave `started`, and a finalization failure returns an uncertain outcome. Neither proves that an upstream write did or did not happen; reconcile before retrying.

## Dashboard browser boundary

The browser uses only same-origin `/api` with an HttpOnly session cookie. The readable CSRF cookie is copied to `X-CSRF-Token` for authenticated writes; an XSS flaw would still be able to act with the user's session, so upstream tool descriptions and errors are rendered as plain text and never injected as HTML. The admin registry form does not retrieve or prefill upstream credentials. Its Keep/Replace/Remove choices map to backend mutations, which still enforce URL and header policy. Gateway API keys and invitation links appear once in in-memory UI state and disappear after dismissal/navigation; copied values remain in the user's clipboard until overwritten. The Connect page uses a placeholder key and public gateway URL only.

The frontend pod has no egress and accepts traffic only from Traefik according to NetworkPolicy. Traefik is also allowed to reach the backend for `/api`; Kubernetes NetworkPolicy cannot distinguish one Traefik route from another, so backend authentication and CSRF remain the security boundary. Local HTTP is demo-only. Production must provide HTTPS for both dashboard and API, Secure session cookies, trusted TLS, and browser security review. The current UI does not add MFA, password reset, central rate-limit storage, or general audit events for registry and login mutations.

## Chat and provider boundary

The browser sends its session cookie and CSRF header to `/api/chat`; it never receives the provider key, delegated bearer, or an upstream credential. The backend issues a signed two-minute delegation bound to the user and originating login-session ID. Its purpose-separated signing key derives from the gateway's existing Fernet Secret, so loss or rotation of that Secret invalidates delegations as well as affecting upstream credential decryption. The delegation is sent only to the backend's loopback gateway endpoint, and the gateway rejects it from non-loopback peers. Gateway transport and execution each re-read session/user status, so logout, expiry, and deactivation terminate authority. A stolen delegation could be replayed locally for its short lifetime by a process inside the same pod; the backend process is therefore a trusted boundary. The chat route never uses a shared administrator key and never accesses upstream MCP Services directly.

The model can choose tool names and arguments, but cannot grant itself more privileges than the delegated user and enabled gateway tools. Prompt injection in upstream descriptions/results can influence model text or tool choices; the system prompt marks them untrusted, the gateway enforces destination and audit controls, and tool/result limits bound exposure. A model response is not proof of a store change; only a successful gateway tool result is. On uncertain write outcomes the loop stops and asks for reconciliation rather than retrying. Audit correlation IDs link UI traces to gateway rows without storing conversation text or tool arguments/results. The frontend renders assistant Markdown through a constrained element set: raw HTML and images are dropped, links are limited to HTTP/HTTPS/mailto without URL credentials, and no HTML string is injected. User messages and gateway traces remain plain React text. Clicked external links are still untrusted sites.

The chart adds backend egress to public IPv4 TCP 443 for Anthropic or public HTTPS MCP registration. Standard NetworkPolicy cannot restrict that rule to an FQDN, so the backend can technically reach any public HTTPS destination; production needs a reviewed egress proxy or FQDN-aware CNI for tighter control. Private, loopback, link-local, carrier-grade NAT, and multicast ranges are excluded from that broad rule, while explicit pod-selector rules retain approved MCP and PostgreSQL access. Node-originated and privileged traffic are outside normal pod policy. The Anthropic SDK's request timeout is bounded and retries are disabled, but a provider outage can make chat unavailable without affecting process liveness or other dashboard functions.

The WP-CLI CronJob holds the store's database password and WordPress salts through the same Secret references as WordPress, so access to its Pod or Secret is sensitive. It mounts the live WordPress content PVC and executes due plugin hooks, which can change store data; a failed or interrupted Job may leave Action Scheduler work pending or in progress. Overlap is forbidden and each run is bounded, but application-level hook idempotency still matters. Cron egress allows MariaDB, CoreDNS, and public IPv4 HTTPS for update checks; standard NetworkPolicy cannot constrain that HTTPS traffic by hostname. The local CNI allowed MariaDB and denied PostgreSQL from a runner pod, but production enforcement requires its own test. Neither the schedule nor retained PVCs replace backups.
