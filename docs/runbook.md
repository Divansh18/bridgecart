# Store runbook

All local commands target `--context k3d-bridgecart` and namespace `bridgecart`; do not rely on the current kubectl context. Start with `make store-status`, `make store-smoke`, and `helm --kube-context k3d-bridgecart status bridgecart -n bridgecart`. For bootstrap failure, inspect the Job status, pod events, and Job logs. Never paste Secret values into logs or tickets.

## Health and data

WordPress startup/liveness use a static file. WordPress readiness uses `/wp-login.php`; if it fails, inspect WordPress logs and MariaDB readiness. MariaDB probes use `healthcheck.sh`. PVCs must be `Bound`. Inspect `kubectl --context k3d-bridgecart -n bridgecart get pods,pvc,events` and check volume ownership if a Job cannot write WordPress files. The official Apache image prepares the volume as UID/GID 33; the WP-CLI Job explicitly runs as 33:33 because its Alpine default differs.

## Scheduled actions

Check `kubectl --context k3d-bridgecart -n bridgecart get cronjob bridgecart-wordpress-cron` and `kubectl --context k3d-bridgecart -n bridgecart get jobs --sort-by=.metadata.creationTimestamp`. Inspect a failed Job's status, pod events, and its safe summary log with `kubectl --context k3d-bridgecart -n bridgecart logs job/<job-name>`. The Job runs every five minutes with `concurrencyPolicy: Forbid`, a 120-second start window, a 180-second run deadline, no immediate retry, and at most two batches of 20 Action Scheduler actions. It waits briefly for MariaDB network policy to apply before opening a connection. It uses the existing store Secret and WordPress PVC, not a copy of either. Natural WordPress WP-Cron spawning is disabled only while `store.cron.enabled=true`.

In WooCommerce admin, use **Status → Scheduled Actions** to inspect pending and failed hooks and their logs. Do not delete overdue or failed actions to clear a notice. A completed Job can still leave a particular action failed; investigate its hook and plugin log. If Jobs stop, check CronJob suspension, the RWO PVC's WordPress-node placement, MariaDB readiness, DNS, public HTTPS egress, and the `bridgecart-wordpress-cron-egress` and `bridgecart-mariadb-access` policies. A failed Job remains for inspection until the CronJob history limit prunes it; the next schedule is the bounded retry opportunity. Do not run a second external cron runner concurrently. For an upgrade or rollback, review whether the target values enable the CronJob so visitor-triggered WP-Cron and the scheduled runner are not both disabled.

To replace pods without deleting PVCs:

```sh
kubectl --context k3d-bridgecart -n bridgecart delete pod -l app.kubernetes.io/component=wordpress
kubectl --context k3d-bridgecart -n bridgecart rollout status deployment/bridgecart-wordpress --timeout=10m
kubectl --context k3d-bridgecart -n bridgecart delete pod bridgecart-mariadb-0
kubectl --context k3d-bridgecart -n bridgecart rollout status statefulset/bridgecart-mariadb --timeout=10m
```

The WordPress Deployment uses Recreate to avoid a simultaneous writer on its RWO volume. The MariaDB StatefulSet keeps one stable pod identity. Verify the same product/order after replacement. This does not test node loss or backup recovery.

## Network checks

The database has only ClusterIP Services; there is no public route. From a WordPress pod, a PHP mysqli connection using its injected environment should succeed. An unlabeled diagnostic pod in the store namespace should time out connecting to `bridgecart-mariadb:3306`, while resolving the Service DNS name. Delete only that diagnostic pod afterward. This is the enforcement check; the presence of NetworkPolicy resources alone is insufficient.

Allowed paths are host `127.0.0.1:8088` → k3d load balancer → Traefik → WordPress TCP 80; WordPress/Bootstrap → MariaDB TCP 3306; WordPress/Bootstrap → CoreDNS TCP/UDP 53; Bootstrap → public HTTPS TCP 443 for the pinned plugin. MariaDB has no permitted egress. Kubelet probe traffic originates from nodes and is not a public store path.

## Upgrade, uninstall, recovery

Before upgrades, back up MariaDB and WordPress content together and test restore. `make store-bootstrap` reruns the idempotent hook; it does not create a duplicate SKU. Changing the pinned WooCommerce version requires explicit `allowPluginUpgrade`, a backup, and compatibility review. Inspect revisions with `helm --kube-context k3d-bridgecart history bridgecart -n bridgecart`. To restore a prior workload manifest, use `helm --kube-context k3d-bridgecart rollback bridgecart <revision> -n bridgecart --wait`, then check pods, PVCs, product, and orders. `make store-deploy` returns to the current local values. Helm rollback does not reverse WooCommerce/WordPress database migrations. `helm uninstall` leaves the store PVCs and, when enabled, the PostgreSQL PVC via resource-policy annotations; a completed hook Job may remain. Inspect and preserve them unless intentional data destruction is separately approved. Never delete an existing k3d cluster or PVC automatically.

## MCP incidents and verification

Run `make mcp-status` and `make gateway-verify`. WooCommerce MCP `/health/live` checks process liveness; `/health/ready` performs one bounded authenticated WooCommerce REST read and returns 503 when WordPress, its database, or the API credential is unavailable. A liveness success with readiness failure should direct investigation to WordPress/API credentials, not trigger a restart loop. Inspect `kubectl --context k3d-bridgecart -n bridgecart logs deploy/bridgecart-woocommerce-mcp` without sharing raw logs. The service suppresses HTTP access logs and never logs Authorization headers or REST bodies.

A write timeout is ambiguous: look up the product by name or order by ID in WooCommerce before retrying. The MCP client never retries writes automatically. For local WooCommerce key rotation, run `python3 scripts/rotate_woocommerce_mcp_key.py`. It creates a replacement key, updates only the dedicated API Secret, restarts the MCP Deployment, waits for readiness, then revokes the old key. Rotate the MCP bearer separately and update authorized gateway clients. `make mcp-secrets` preserves existing values and does not rotate. The API key is distinct from the WordPress admin password.

Network controls: only the backend gateway pod may reach the three upstream MCP Services; the milestone-three temporary exception has been removed. WooCommerce MCP egress reaches WordPress TCP 80 and CoreDNS TCP/UDP 53; inventory and shipping have no allowed egress, and none of the three may reach MariaDB or PostgreSQL. The milestone-three verification used positive controls (labeled client → MCP and MCP → WordPress both connected) and negative controls (unlabeled client → MCP and MCP → MariaDB returned connection refusal). Check actual connections because a rendered NetworkPolicy alone does not prove enforcement. The milestone-three temporary Pod workflow is retired; use `make gateway-network-verify` for current enforcement checks.

## Team API

Run `make backend-status` and check `http://api.bridgecart.local:8088/health/live` and `/health/ready` with the API host mapped to loopback. Liveness is database-independent; readiness checks PostgreSQL and Alembic revision `20261012_01`. Inspect the failed `bridgecart-backend-migrate` Job and pod events if readiness stays 503 after an upgrade. The migration Job is a pre-upgrade Helm hook, so a failed manifest apply after migration can briefly leave the old backend unready; fix the chart and complete the forward upgrade promptly. Do not print Secret data while diagnosing. Rerunning `make backend-deploy` preserves existing admin credentials, users, sessions, invitations, API keys, and the PostgreSQL PVC.

`make backend-verify` creates and drops only its own random test database. `make backend-live-verify` is a deliberate live check: it creates or reuses the `milestone4a-member@bridgecart.local` account, `bridgecart-demo-member` Secret, and two named keys; it replaces only the backend pod after checking its ownership label. These are retained test artifacts. The test scans logs for the credential values it used but does not print them. For a manual network check, an unlabeled pod should fail to reach `bridgecart-postgres:5432`, while `/health/ready` should remain 200 as the positive backend control. Verify actual connections, not only rendered policies.

The PostgreSQL claim is marked `helm.sh/resource-policy: keep` on uninstall; inspect it before any intentional removal. Its local-path volume may be lost with the k3d node or cluster. Back up PostgreSQL separately from MariaDB and WordPress content. Before a backend upgrade, test the migration and backup restore. Roll back manifests only with a compatible schema; Alembic and application writes are not automatically reversible. If a user is deactivated or an API key revoked, the next authenticated request is denied because the verifier checks PostgreSQL every time. Session and API-key credentials have distinct stores and cannot be interchanged.

## Gateway incidents and recovery

Run `make gateway-status`, `make gateway-verify`, `make gateway-outage-verify`, and `make gateway-network-verify` from the project root. The live verification creates two short-lived keys and revokes them, leaving audit rows but no store product/order writes. The outage script scales only the owned shipping Deployment from one replica to zero, verifies `Unreachable` while the other two servers still work, then restores one replica in a `finally` block. `make server-control-verify` additionally checks admin disable/restore, a member's refreshed MCP list and cached call, browser chat behavior, ownership-checked Shipping pod replacement, a sustained scale-to-zero outage, safe audit outcomes, and final workload readiness. It uses system Python Playwright for the browser step and revokes its temporary member key in cleanup. If interrupted, check `kubectl --context k3d-bridgecart -n bridgecart get deploy bridgecart-shipping-mcp` and restore its prior replica count deliberately. The network script creates one random ownership-labeled Pod and deletes it only after checking the UID; inspect any leftover Pod before manual cleanup.

An unhealthy upstream does not fail backend readiness. Use admin `GET /servers` for `Connected`, `Unreachable`, or `Disabled`; the safe reason is a category, not a raw upstream response. Check the affected Deployment readiness, its ClusterIP Service, DNS, Secret references, and NetworkPolicy. `Unreachable` entries are retried on the next discovery after at most five seconds of failure cache; healthy tools remain listed. A normal catalog caches for 15 seconds in the one backend process. Clients should explicitly call `tools/list` after a registry edit or outage recovery; this stateless MCP server does not send tool-list push notifications. Dashboard chat refreshes discovery on every turn. Even if a client holds an old tool name, the gateway checks the registry before dispatch and records a rejected attempt. A cached call to an enabled but unreachable server returns safe `upstream_unavailable` rather than implying that the name never existed.

For a user-key incident, revoke the key through `DELETE /api-keys/{id}` or an admin member-key route; the next transport request on an existing client connection returns 401. For an upstream-bearer incident, create a replacement Secret value through a controlled process, update the corresponding encrypted registry credential with admin `PATCH /servers/{id}`, and restart the affected upstream Deployment to load the new bearer. Coordinate the order so the gateway and service agree; do not paste credentials into command arguments or logs. Back up the `bridgecart-upstream-encryption` Secret with PostgreSQL. Losing that key makes existing encrypted registration credentials unrecoverable; simply creating a new key will not decrypt them.

`GET /audit` shows started and finalized attempts with user/key/server snapshots. A `started` row after a crash means the outcome is unknown, not that the write failed. If audit insertion fails, the tool is not dispatched. If finalization fails, the caller receives an uncertain-outcome error while the earlier `started` row remains. For write timeouts or interrupted calls, inspect the target WooCommerce resource or order before retrying. Do not use Helm rollback to assume PostgreSQL migrations, registry edits, audits, or upstream writes are reversed. Keep the existing store and all three PVCs during incident response.

## Dashboard checks and recovery

Run `make dashboard-status` and `make dashboard-smoke`. The smoke check verifies the root page, reloaded `/servers` and `/api-keys` SPA routes, runtime gateway URL, and that unauthenticated `/api/auth/me` returns FastAPI 401 rather than the SPA HTML. Check `kubectl --context k3d-bridgecart -n bridgecart describe ingress bridgecart-dashboard-api` if `/api/` fails; the `bridgecart-dashboard-api` Traefik Middleware must exist and strip `/api`. The API host's `/mcp` Ingress remains separate. If a login succeeds but later mutations fail with 403, check the readable CSRF cookie and same-origin `X-CSRF-Token` request header; do not copy raw cookie values into incident logs.

`make dashboard-deploy` imports pinned frontend and backend images and upgrades the current release with `frontend.enabled=true` and `store.bootstrap.enabled=false`, so the UI upgrade does not rerun WP-CLI. It runs the idempotent backend migration hook. On a fresh cluster, complete store and gateway setup first. Inspect `helm history` and pod events before a rollback. Helm rollback may restore an older frontend image but will not undo PostgreSQL, WordPress, or WooCommerce data changes. The frontend has no persistence; users, keys, registry, and audit records live on PostgreSQL's retained PVC.

## Chat checks and recovery

After `make anthropic-secret`, run `make dashboard-deploy`, `make dashboard-status`, `make backend-verify`, `make gateway-verify`, and `make dashboard-smoke`. Open `/chat` on the dashboard as a team user. The local model is `claude-sonnet-4-6`. A missing key or model returns `503 Chat is not configured` while other features remain healthy. Secret updates require a backend rollout because env vars do not refresh in place. Inspect only Secret field names and `secretKeyRef` metadata; never print the key or use `kubectl describe` output as a credential store. The migration Job must not receive Anthropic configuration.

For a failed chat turn, record its correlation ID (when returned), safe UI error, and relevant `/audit` rows. Provider 429 is rate limiting; 503 may be provider auth/network or missing configuration; 502 can indicate truncation or tool bounds. The backend suppresses raw SDK/upstream errors. A timeout after a product/order write is uncertain: inspect WooCommerce and the audit outcome before retrying. Do not assume Helm rollback reverses migration `20261012_01` or store writes. If a demo upstream is disabled, the next chat turn lists tools afresh; a cached direct call is still rejected. Restore any intentionally disabled server through the admin dashboard/API. Check `bridgecart-backend-chat` ServersTransport and the production entrypoint/load-balancer timeout if requests are cut off before the 45-second application deadline.
